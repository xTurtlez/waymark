# Waymark v2 plan

Working from the v2 brief (`claude/v2-build-prompt.md` in the Waymark project) and the v1 assessment. v0.1 (`ee9d54f`) is the starting point. Work happens on `v2`, one PR per milestone, conventional commits.

## Milestone 1: Foundation

**Goal:** the v1 product runs on a real database with real accounts. Tenancy is enforced by Postgres, every change is written to a tamper-evident audit log, files have somewhere safe to live, and there's a job queue. The public GitHub Pages demo keeps working.

### Decisions (within the brief's fixed architecture)

| Area | Decision | Why |
|---|---|---|
| Driver | `postgres` (postgres.js) + Drizzle ORM; migrations generated by drizzle-kit into `drizzle/`, plus hand-written SQL migrations for roles, RLS forcing, triggers. | Works with Neon (TCP) and plain Postgres in CI and dev. |
| Tenancy | Every tenant row carries `firm_id`. Each request runs in a transaction that does `SET LOCAL ROLE waymark_app` and sets `app.firm_id`, `app.user_id`, `app.scope` (`firm` / `portal`) with `set_config(..., true)`. `waymark_app` is NOLOGIN, NOBYPASSRLS and not the table owner, so policies always apply, even if the login role is privileged (it often is on Neon and locally). | RLS is in the database, not app code. One connection string is enough. |
| Portal scope | In `portal` scope, estate-level policies also require an `estate_party` row linking `app.user_id` to the estate. | Executors see only their estates, even within the firm. |
| Auth | **Better Auth** with the Drizzle adapter. Staff: email + password with TOTP (two-factor plugin), passkeys. Families: magic links (+ optional passkey). Microsoft Entra SSO is configured only when its env vars are set. Firm roles live in `membership`; family roles in `estate_party`. | One library covers every method in the brief. Auth tables are global (a person can be staff at one firm and an executor elsewhere). |
| Email | `Mailer` interface. `outbox` driver (writes to the `outbound_message` table, readable at `/dev/outbox` outside production) for dev and CI; `postmark` driver over HTTPS when `POSTMARK_SERVER_TOKEN` is set. | Magic links are testable end to end without an email account. |
| Files | `Storage` interface: `s3` (AWS SDK, `eu-west-2`, SSE, signed URLs) and `local` (disk, dev only). Uploads are sniffed by magic bytes against an allowlist, hashed (SHA-256), size-capped, and passed to a `MalwareScanner` interface (`eicar` dev scanner now; ClamAV/managed scanner adapter later). Image/PDF normalisation lands with guided capture in M5. | UK residency and integrity from day one; no account needed to develop. |
| Audit | `audit_event` is append-only (UPDATE/DELETE blocked by trigger and not granted) and hash-chained per firm in a trigger: `hash = sha256(prev_hash ‖ canonical row)`, serialised with a per-firm advisory lock. `audit_verify(firm)` recomputes the chain. AI actions attach prompt/output. | Tamper-evident without trusting app code. |
| Jobs | Postgres `job` table with `FOR UPDATE SKIP LOCKED` claiming, retries with backoff and dedupe keys. Run by Vercel Cron (`/api/jobs/run`, `CRON_SECRET`) and opportunistically via `after()` following mutations. Handlers run inside the job's tenant context. | No extra service; works on Vercel. Can move to Inngest later behind the same `enqueue()` API. |
| Data in M1 | Normalised tables for firm, staff, estate core, parties and documents. The rest of each v1 estate lives in `estate.workspace` (JSONB) until M2 replaces it with the full schema. Mutations run the existing v1 reducer server-side, write back, and audit before/after. | Gets every v1 screen onto the DB now without building the M2 schema twice. |
| Demo build | `WAYMARK_MODE=demo` builds a static export with the v1 seed and local store (GitHub Pages). Mode-specific files use `*.live.tsx` / `*.demo.tsx` via `pageExtensions`; shared screens are plain `*.tsx`. | Keeps the public demo link alive from the same codebase. |
| Hosting | Vercel, `lhr1` (`vercel.json`). Neon or Supabase in London (`eu-west-2`). Not provisioned yet: CI runs everything against Postgres 16. | Deploy waits for Tom's accounts. |
| Dev tooling | npm is blocked in Claude's workspace, so CI publishes `node_modules` to an orphan `devdeps` branch (force-pushed, single commit) when dependencies change. | Lets changes be tested locally. Delete the branch any time. |

### M1 deliverables

1. Dependencies, ESLint, Vitest, Playwright, CI (`ci.yml`: lint → typecheck → unit → migrate + seed → build live → E2E live → build demo → E2E demo).
2. Schema + migrations: `firm`, `membership`, Better Auth tables, `estate`, `party`, `estate_party`, `file_object`, `audit_event`, `job`, `outbound_message`; roles, grants and RLS policies.
3. `withTenant()` data access, server actions for every v1 store action, audit on each.
4. Auth flows: staff sign-in (password, TOTP, passkey), account security page, family magic link, sign-out, route protection (`proxy.live.ts`).
5. Storage + upload route with sniffing, hashing, scanning; portal document upload stores real files.
6. Job queue + runner + first handler (`audit.verify` nightly).
7. Seed: Ellis & Rowe demo firm from the v1 seed, plus a second firm used by the tenancy tests.
8. Tests: RLS cross-firm read/write fails (both scopes), audit append-only + chain verifies, job claiming is exactly-once, upload validation; E2E sign-in → approve draft → audited; magic link → portal; demo build parity.
9. `README.md`, `.env.example`, `docs/deploy.md` (Vercel + Neon steps for Tom).

### Out of M1

Full domain model (M2), rules engine (M3), transactions (M4), IDV, signatures and quiet hours (M5), model-backed AI (M6), PDFs (M7), branding and metrics (M8).

## Milestone 2: Real data model

**Goal:** the estate record lives in proper tables with real dates. Stage, waiting-on, the blocker line and needs-attention are derived, never stored or typed in.

### Decisions

| Area | Decision | Why |
|---|---|---|
| Tables | `estate` (deceased details, service level, status, fee estimate), `estate_party` (+ key, primary, IDV status), `estate_staff`, `milestone`, `will`, `will_gift`, `institution` (shared, read-only to the app), `holding`, `ledger_entry`, `task`, `document`, `extraction`, `draft`, `missing_item`, `message`, `client_update`, `note`. Every tenant row carries `firm_id` + `estate_id` and a per-estate `key` (the id the screens use). | Matches the brief's domain model. The keys keep URLs and the shared reducer stable. |
| Business logic | One pure reducer (`src/lib/reducer.ts`) for both builds. The live server action runs it inside the tenant transaction, then `saveEstate()` writes only the rows that changed. `loadEstates()` assembles the screens' shape from the tables. | Demo and live can't drift; every action still runs server-side under RLS. The Transaction Engine (M4) adds server-only domain services alongside. |
| Dates | Calendar days as `date`, moments as `timestamptz`; ISO strings in the app. "Today", "Fri" and "3 weeks, overdue" are computed in UK time (`src/lib/format.ts`), so labels match on a UTC server and a phone in Bath. | Brief: no display strings in the database. |
| Derived values | `src/lib/derive.ts`: stage = first milestone not reached; waiting-on = the most urgent open third-party task (overdue first, then earliest due), else the family, else none; attention = something overdue, an HMRC deadline within 14 days, or a family task open over 28 days. Holding status wording and journey timing are derived the same way. | One tested place; the dashboard, cards and portal all agree. |
| Audit trail on screen | Read from `audit_event` (the real hash-chained log), latest 50 per estate, firm scope only. Each action writes one event with row-level before/after. | No second, editable copy of history. |
| Visibility | Families: their estate's holdings, documents, messages, updates, milestones and their own tasks. They may create a "please check my upload" task for the firm. Firm-only: notes, drafts, extractions, missing items, will, ledger, audit. No DELETE grants on estate tables. | Least privilege in the database, proven by tests. |
| Migrations | Pre-release, the M1 migrations were folded into a clean baseline (`0000_init` generated + `0001_security` hand-written). Nothing had been deployed. | Avoids a rename migration before launch. From the first production deploy, migrations are append-only. |
| Demo freshness | The seed is built relative to "now", so the demo always reads the same (Barclays three weeks late, valuation in five days). | Real dates without a stale demo. |

### Deliverables
Schema + RLS for every new table; `estate-store.ts` (load/save); derived fields everywhere; seed rewritten onto the same save path; tests: date helpers, derivation, reducer, full save→load round trip, family visibility and write limits, no deletes, RLS on every `firm_id` table.

## Milestone 3: Rules engine and IHT workspace

**Goal:** a pure, dated, fully tested Inheritance Tax and intestacy engine, wired to the estate record, with an explainable breakdown a solicitor can check and export.

### Decisions

| Area | Decision | Why |
|---|---|---|
| Engine | `src/rules/`: pure TypeScript, no I/O. `calculateIht(input)` returns figures, an ordered `Line[]` breakdown (each with its source link), flags, who bears the tax, transferable allowances, reporting route and IHT400 schedules, and the payment date. | Brief section 8: explainable, testable, the same in both builds. |
| Rules as data | `src/rules/tables.ts`: every rate and threshold is a dated row with a source URL; `rulesFor(dateOfDeath)` picks the rows in force. Confirmed to 5 April 2030; later deaths get a `rates_unconfirmed` flag. Deaths before 6 April 2017 are out of scope. | Rules change by date of death, not by release. |
| Scope | Death estate, grossing up (single and double), s.39A attribution of reliefs, Ratcliffe residue, the 36% charity rate per component (with merge election), RNRB with taper, brought-forward and downsizing, BPR/APR including the £2.5m allowance from 6 April 2026, pensions in the estate from 6 April 2027, lifetime gifts (exemptions, cumulation incl. the 14-year shadow, taper relief), QSR, excepted-estate route, intestacy (per stirpes). | Brief section 8 list. |
| Not guessing | Where the law or HMRC guidance is unsettled the engine raises a **confirm** flag that a solicitor ticks in the IHT tab; unsupported situations raise **out of scope** and mark the result incomplete. Each is listed in `docs/open-legal-questions.md`. A confirmation is stored with the wording confirmed, so it lapses if the figures change. | Brief: never silently guess a rule. |
| Tests | 69 hand-checked worked estates (`tests/rules/fixtures.ts`, each with its working in prose) plus unit tests; 100% statement and branch coverage enforced on `src/rules/**`. | Brief: fixture suite ≥ 40, full coverage. |
| Inputs | New firm-only tables: `iht_profile` (one per estate: residence, transferred bands, predeceased spouse, downsizing, elections, intestacy family, confirmations), `lifetime_gift`, `prior_transfer`, `holding_tax` (ownership, home for RNRB, reliefs, pensions, foreign, secured debts) and `party_tax` (spouse / charity / descendant). `will_gift` links a specific gift to its holding and records "bears its own tax". | Families can read `holding` and `estate_party`; tax treatment lives beside them, not in them, so RLS keeps it firm-only and a family edit can't reset it. |
| Defaults | Tax category comes from the recorded relationship (wife, son…) unless a solicitor sets it, and the screen says so. Unvalued holdings count as nil with a warning. Missing date of death or succession blocks the calculation with a plain explanation. | Assumptions are visible, never silent. |
| Screens | IHT tab: summary tiles, gaps and assumptions, the breakdown (CSV download and print), who bears the tax, points for a solicitor, holdings, allowances and elections, the will (or intestacy shares), beneficiaries, gifts, earlier estates, and allowances left for a surviving spouse. The overview card and the assistant use the engine too. | Brief: explainable breakdown, exportable by a solicitor. |

### Deliverables
Engine + fixtures; migrations `0002_iht` and `0003_iht_security` (grants and firm-only RLS); store load/save; reducer actions with zod validation (staff-only) and audit entries; IHT tab and sheets; seeds covering a taxable estate (Mehta), excepted estates with transferred bands (Ellis, Asante) and an intestacy (Reid); E2E at 1440px and 390px on live and demo.
